# Numbra — Roadmap and acceptance tests

**Protected file.** The autopilot harness reverts any change an agent makes here, so the
goalposts cannot move during an unattended run. Humans edit it between runs.

Numbra is a **proof of concept**: an offline Android app that helps community health
volunteers in Nepal screen skin lesions for possible leprosy and **refer** suspected cases.
It is a triage aid, never a diagnosis. The run succeeds when every milestone below has
passed review (or reached the review round limit) **and** `scripts/check.sh` is green with
a debug APK built.

Each milestone ID (M0, M1, …) is also its review folder: `reviews/M0/`, `reviews/M1/`, …

---

## M0 — Research and plan
Brief: `prompts/codex-phase0-research.md` (ignore its Step 4; the harness runs reviews).
Acceptance:
- All `research/0x-*.md` documents, `docs/01-phase0-synthesis.md`, and ADRs for task
  framing, dataset selection and licensing, code licence, and data-contribution governance.
- Every dataset claim has a source link or is marked `UNVERIFIED`.

## M1 — ML project scaffold
Acceptance:
- `ml/` is a Python project (`pyproject.toml`, pinned dependencies, `ml/tests/`).
- Data-loading interfaces, a dataset manifest schema (source, licence, label, confirmed-by,
  patient/group id, split), and the unified label taxonomy from M0 as code.
- Tests run on a tiny **synthetic** fixture (generated in code, not real images) and pass.

## M2 — Data acquisition and preparation
Acceptance:
- Scripts download **only** datasets that ADR-dataset approves and whose licence allows
  this use without signing an agreement or creating an account. Data lives under
  `data/` and is never committed.
- Generated manifest with licence per row; duplicate detection; **patient/group-level
  splits** and at least one held-out source for leave-one-source-out testing.
- If no suitable real data is obtainable, say so plainly in `notes/HUMAN-QUEUE.md`, keep
  the pipeline working on synthetic data, and label every downstream model **PLACEHOLDER**.

## M3 — Baseline classifier
Acceptance:
- A CPU-trainable transfer-learning model (e.g. MobileNetV3 or EfficientNet-Lite class)
  with optional metadata fusion, trained by one reproducible command.
- `ml/reports/` evaluation generated by script: sensitivity at a fixed high-sensitivity
  operating point, specificity, AUC, calibration, per-source and per-skin-tone breakdowns
  where labels exist, and a leave-one-source-out result.
- A model card stating data, limitations, intended use, and whether the model is a
  PLACEHOLDER.

## M4 — On-device model export
Acceptance:
- Export to LiteRT/TFLite (or ONNX Runtime Mobile if the ADR chooses it), quantised.
- A parity test: exported model vs Python model on the same inputs, within a stated tolerance.
- Model file ≤ 20 MB; the input preprocessing spec is written down and tested.

## M5 — Android app skeleton
Acceptance:
- `app/` Kotlin Android project (Jetpack Compose suggested; an ADR may choose otherwise),
  minSdk chosen for low-end devices and justified in an ADR.
- `./gradlew testDebugUnitTest assembleDebug` passes from `app/`.
- Works fully offline; English and Nepali string resources (Nepali flagged for native review).

## M6 — Screening flow
Acceptance:
- Capture or pick a lesion photo, with an image-quality check (blur, exposure).
- Guided questions: sensation test of the patch (with instructions), number of patches,
  duration, nerve symptoms, contact history.
- On-device inference with the M4 model.
- A **transparent referral rule engine**, unit tested, combining model output and answers.
  It must **never** output "no leprosy" or equivalent: possible outcomes are of the form
  "refer", "refer urgently", or "low concern from photo, refer if sensation loss or
  change". A test asserts this.

## M7 — Records, referral and data model
Acceptance:
- Encrypted on-device storage of screenings; neutral app wording (no "leprosy" on the
  home screen or notifications).
- A shareable referral summary (text/PDF) for the clinic.
- A data-contribution record model with consent, provisional vs confirmed label and
  provenance fields, plus an export format. **No server and no upload** in this POC.

## M8 — Hardening and end-to-end test
Acceptance:
- An end-to-end JVM test (e.g. Robolectric) running the whole flow on a bundled synthetic
  test image through to a referral outcome.
- Basic accessibility (content descriptions, large touch targets), a user guide in
  `docs/`, and `docs/FINAL-REPORT.md`: what works, what is placeholder, what humans must
  do next (clinical validation, ethics, native-language review).
- `scripts/check.sh` green; debug APK produced.
